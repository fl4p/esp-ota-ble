# esp-ota-ble: three defects found integrating it into a LoRaWAN sensor node

Found 2026-09-07 while adding a fourth consumer (`ha/farming/tech/node-prototype`,
an ESP32-S3 compost-pile node). Ordered by consequence. **#1 reaches
`fugu-mppt-firmware` and stops the converter.**

Nothing here was reproduced on hardware — these are read from the source, and #1
is a race whose window is one tick period, so it is exactly the kind of thing
that would not show up in a bench test. Treat them as hypotheses to confirm, not
as measurements.

---

## 1. A `begin` that is latched and then disconnected can never be aborted

`otaBleSubmitCommand()` **latches** on the producer task and `otaBleTick()`
executes on the consumer task (`ota_ble.cpp:214-236`) — deliberately, and the
README explains why. But `otaBleRequestAbort()` early-returns while the transfer
is not yet active:

```c
void otaBleRequestAbort() {
    if (!active) return;      // ota_ble.cpp:281
    abortReq = true;
}
```

So this sequence leaves an unabortable transfer:

1. client writes `begin <size> <sha>` → `pending = Begin`, `active` still false
2. client disconnects → consumer wires this to `otaBleRequestAbort()` → **no-op**
3. next `otaBleTick()` runs `beginWithDigest()` → `quiesce(true)`, `esp_ota_begin`,
   `active = true`, and critically `abortReq = false` (`ota_ble.cpp:129`)

Nothing now clears it. The peer is gone, so no more bytes arrive; there is no
stall timeout in the module; and the next client's `begin` is refused with
`OTAB FAIL already-active`. The device stays quiesced until it is rebooted.

**Why this is worse than a wasted OTA slot.** `quiesce(true)` has already fired.
In `fugu-mppt-firmware/src/tele/console_ble.cpp:44-50` that is:

```c
static void otaQuiesceHook(bool halt) {
    if (halt) stopAndBackoff(10);
    adcSampler.halted = halt;
}
```

— an MPPT solar charge controller **stopped and not charging, indefinitely**,
from a BLE client that connected, wrote one line and dropped the link. In
`smart-shunt-fw` it halts sampling (`g_samplingHalted`); telemetry stops.
Neither consumer has any recovery path: both call `otaBleRequestAbort()` on
disconnect (`console_ble.cpp:234`, `ble.h:1236`) and nothing else.

The window is one tick period, so it is narrow — but a client that drops the
link *immediately* after writing `begin` is not exotic (a crashed host tool, a
laptop lid closing, a macOS CoreBluetooth teardown), and the consequence is
unbounded in time.

**Suggested fixes**, either or both:

- In `otaBleSubmitCommand()`, let `abort` clear a latched `Begin` instead of
  latching behind it. Cheap, but does not help the disconnect case, which never
  sends `abort` at all.
- Better: give the module the stall timeout it currently lacks (see #3), which
  bounds every variant of "the host went away" rather than this one.
- What the new consumer does, as a workaround at the consumer level: abort when
  `otaBleActive()` is true and no client is connected. That tests the *peer*
  rather than the *request*, so it does not care which order the latch and the
  disconnect landed in. It cannot be done inside the module, which has no idea
  whether a link exists — which is arguably an argument for a
  `otaBleNotePeer(bool)` entry point.

## 2. A lost `CRED` notification is unrecoverable, and the host tool documents a
recovery that does not exist

`grantCredit()` is called **only from inside `if (drained)`** in `drainRing()`
(`ota_ble.cpp:196-202`). So the device re-announces credit only when bytes
actually moved to flash. If a `CRED` notification is lost, the host stops
streaming (it must never pass the high-water mark), the ring drains to empty,
`drained` goes false, and the device never speaks again. Both sides wait.

`fugu-mppt-firmware/etc/ota_ble.py` and `pwr-metering/smart-shunt-ota-ble.py`
both retry three 20-second windows here, with the comment:

> A weak link can lose a CRED notification, but the device keeps flushing and
> re-grants at the next step — so retry a few short windows rather than
> hard-failing on the first gap.

The premise is false: with the host stalled there is no "next step". The retry
only costs 60 seconds before reporting the same failure. (In practice ATT
notifications are acknowledged at the link layer, so loss is unlikely — but the
comment asserts a recovery mechanism that is not there, and someone will
eventually rely on it.)

**Suggested fix:** re-announce the current high-water mark unconditionally every
N ticks while `active`, or drop the `if (drained)` guard and rely on the
`CRED_STEP` hysteresis (which already exists precisely to limit notify spam) to
keep it quiet.

## 3. Ring overrun is silent until `end`, and then reports the wrong thing

`otaBleStageBytes()` on overrun (`ota_ble.cpp:155-158`):

```c
if (len > RING_CAP - rCount) {   // host overran its credit window
    failed = true;
    return;
}
```

The bytes are dropped, `failed` is latched, and **nothing is emitted**. The host
keeps streaming to the end, then waits for `OTAB PROG <size>/<size>` which can
never arrive — `written` is short by whatever was dropped — and times out after
30 s. Only if the host then sends `end` anyway does it learn anything, and the
message is `OTAB FAIL incomplete`, which describes a truncated *upload* rather
than a *protocol violation by the host*.

Not emitting from inside `ringMutex` on the producer task is the right instinct.
But the consumer could notice `failed` in `otaBleTick()` and emit there — one
line, and it turns a 30-second silent timeout into an immediate, correctly named
failure.

Related nit, same function's caller: `otaBleSubmitCommand()` checks
`if (parsedSize == 0 || parsedSize > UINT32_MAX)` (`ota_ble.cpp:~310`).
`unsigned long` is 32 bits on ESP32, so the second half is always false. Harmless
— `parsedSize > next->size` catches oversize two lines later — but it reads as a
guard that is not there.

## Not bugs (checked, and they hold)

- The `active` / ring teardown is properly serialised: `otaBleAbort()` and
  `otaBleEnd()` both clear `active` *inside* `ringMutex` alongside `freeRing()`,
  and `otaBleStageBytes()` re-checks `active` under the same lock. The comment at
  `ota_ble.cpp:153` saying so is accurate.
- `OTA_WITH_SEQUENTIAL_WRITES` versus `OTA_SIZE_UNKNOWN`: the comment is right
  and the reasoning about starving the idle task is right.
- The credit arithmetic `g = written + RING_CAP` is exactly the free space given
  the host has sent `written + rCount`. Sound.
- `mbedtls_sha256_free()` is never reached on an uninitialised context, because
  every path to it is gated on `active`, which is only set after
  `mbedtls_sha256_init()`.
- `sscanf(p, " %lu %79s", ...)` into `char shaHex[80]` does not overflow.
